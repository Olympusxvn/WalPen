# feat(sdk/relayer): expose a recovery plan for failed remember jobs

Status: proposal only; not posted as a second GitHub issue.

## Motivation

In WalPen's 2026-09-19 test with TypeScript SDK 0.1.7, three accepted writes reached terminal failure with `Upstream Unavailable: Memory encryption backend is unavailable`. Two other jobs in the batch succeeded. Replacement application revisions later succeeded after the failed job statuses were inspected.

The recorded response explained the broad dependency problem, but did not establish whether a new submission was safe. Applications should not infer retry safety or storage side effects solely from error text.

## Proposed feature

Expose structured recovery advice in job status and SDK exceptions. Illustrative schema, not current SDK syntax:

```json
{
  "job_id": "existing-job-id",
  "status": "failed",
  "failure": {
    "component": "seal",
    "stage": "encryption",
    "code": "UPSTREAM_UNAVAILABLE"
  },
  "recovery": {
    "action": "wait_then_retry",
    "retry_after_ms": 5000,
    "storage_outcome": "not_started",
    "correlation_id": "public-support-reference"
  }
}
```

The server must derive `storage_outcome` from durable stage/checkpoint evidence, not guess it from the error string. Possible outcomes include `not_started`, `confirmed`, and `unknown`. For an unknown outcome, advice must request reconciliation rather than a new write. A polling timeout should instead say to keep checking the existing job.

The feature should reuse any existing error taxonomy, idempotency mechanism, and job status API. It does not require a new generic idempotency API or imply that no such mechanism exists in newer versions.

## WalPen UX enabled by this

- Show “The relayer's encryption service is temporarily unavailable” separately from invalid credentials or quota errors.
- Show “Still checking the existing job” for polling timeouts.
- Enable a retry action only when the service supplies a safe recovery path; otherwise keep the local journal and request reconciliation.
- Include a non-secret support reference when reporting an incident.

## Acceptance criteria

1. A typed SDK result preserves the job ID and recovery fields without parsing text.
2. A failure before storage and a failure after storage produce different recovery advice.
3. Unknown outcomes never recommend blind resubmission.
4. Retry advice has bounded backoff and uses the existing authorization and deduplication boundaries.
5. Mocked outage/recovery tests verify no duplicate logical memory and that recovery survives a restart.
6. SDKs can handle older servers that omit these fields, without assuming retry is safe.
