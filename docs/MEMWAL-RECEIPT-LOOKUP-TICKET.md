## Request
Expose an authenticated **read-only receipt lookup by caller-supplied idempotency key** for remember jobs, with documented retention semantics.

The TypeScript SDK already accepts `idempotencyKey`, and `getRememberStatus(jobId)` exists. This is a narrower follow-up to those features, not another request to add write deduplication.

## Use case
WalPen can persist a journal revision and its key before sending. If the relayer accepts the write but the HTTP response is lost, the app may restart knowing the key but not the job ID.

Replaying `remember()` with the same key can recover an acknowledgement when the retained mapping exists. However, that is a write endpoint: if the mapping was purged or never existed, replay can create a job. Semantic recall also cannot establish an exact acceptance receipt.

A read-only lookup would let the app inspect this state before deciding what to do.

## Proposed API (illustrative; not existing syntax)
```ts
const receipt = await client.getRememberReceipt({
  namespace: persistedNamespace,
  idempotencyKey: persistedKey,
});
// found: { job_id, status, blob_id?, error? }
// or a documented not-found/expired/unknown result
```

## Required semantics
- Scope and authenticate lookup by the same account/owner and namespace boundary as write deduplication.
- Never create a job, perform a paid upload, or resurrect a deleted memory.
- Return the mapped job ID and current status when retained; then callers can use existing polling.
- Define retention across process restarts, TTL expiry, forget/delete, and terminal job failure.
- A missing or expired mapping must not claim that no write ever occurred. Preserve an explicit unknown outcome when the server cannot distinguish it.
- Document the race between lookup and any later write; actual deduplication must remain atomic at the write endpoint.
- Do not permit cross-account key enumeration or disclose memory contents through lookup.

## Acceptance criteria
- A simulated lost acceptance response followed by a new client process can recover the original job ID by key without invoking `remember()` again.
- Repeated lookups produce no extra jobs/blobs.
- Tests cover account/namespace isolation, completed/failed/pending jobs, retention expiry and forget/delete.
- SDK typings and recovery documentation clearly distinguish receipt lookup, same-key replay and creating a replacement revision.
