## Request
Add a durable application example for recovering `remember()` submissions after transport timeouts, polling timeouts, and process restarts.

This is a documentation request, not a claim that MemWal lacks idempotency or job polling. The installed TypeScript SDK `@mysten-incubation/memwal@0.1.7` already exposes:

```ts
const accepted = await client.remember(text, namespace, {
  idempotencyKey: persistedKey,
});
await client.getRememberStatus(accepted.job_id);
await client.waitForRememberJob(accepted.job_id);
```

## Why the happy-path example is insufficient for WalPen
WalPen stores journal revisions locally and submits them asynchronously. Recovery needs to distinguish:

| Situation | Application must preserve |
|---|---|
| Accepted job, polling timeout | The original job ID; keep checking rather than create a replacement |
| Transport failure before acceptance response | The original payload, namespace and caller-supplied key; outcome remains unknown |
| Process restart during submission | Persisted intent from before the request; do not rely on a client's in-memory generated key |
| Server reports terminal failure | Failure evidence; distinguish an exhausted failed job from a pending/unknown outcome |
| Status/key is no longer found | Retention/deletion semantics; absence is not automatically proof the write never happened |

Our live five-page test encountered terminal encryption failures (#1047). Separate application regression tests inject ambiguous transport outcomes. We are not claiming all failure scenarios occurred on Mainnet.

## Requested example
A small SQLite/file-backed recipe covering:
1. Persist immutable payload, account/namespace scope and a stable idempotency key before submission.
2. Persist the returned job ID.
3. Resume polling after restart using that ID.
4. Recover a lost acceptance response using the supported same-key behavior, explicitly documenting payload conflicts, key lifetime and terminal-failure behavior.
5. Explain when replacement writes are safe and when reconciliation is required.
6. Avoid duplicate writes and false "saved" messages in UI.

If an exact receipt lookup by key is unavailable, document that limitation instead of treating semantic recall as an exact receipt.

## Acceptance criteria
- Copyable code uses supported SDK APIs and states a tested SDK version.
- Offline failure-injection tests cover a lost acceptance response, polling timeout and restart.
- The example never automatically generates a new key after an ambiguous outcome.
- It explains that replaying a write and querying its receipt are different operations.
- Links from `rememberAndWait()`/quick-start docs point to this recipe.
